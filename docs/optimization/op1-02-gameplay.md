# 第 2 轮优化 · 对局与规格机制

> 本文件收录第 1 轮反馈实施中与「对局与规格机制」相关的条目，原始意见与总索引见 op1.md。掷骰同点自动重掷、开局前强制规格协商（提议-应答 + 每局重确认）、重开/下一局双同意投票制。

## 反馈 5：掷骰逻辑有问题——双方同点后重掷一直同点

### 你的想法

> 投骰子部分我觉得逻辑有些问题，我刚才二者都摇到了 6，然后再往后二者的数就一直一样，随机摇数的逻辑要加强一下。

### 我的想法与排查

- 先说随机源：`crypto.randomInt(1, 7)` 是 Node 加密级随机、每次调用独立，**随机本身没有缺陷**，也不存在"两边摇到同一个数"的相关性 bug；
- 真正的问题在**同点重掷的交互设计**：旧逻辑双方同点后保持 {6,6} 展示、要求两人再各点一次"重新掷骰"，再同点就再来一轮——连续同点时体验就是"数一直一样"地循环点按钮（连续 n 次同点概率 (1/6)ⁿ，虽小但撞上一次就很难受）；
- **加强方案：同点死循环从交互里彻底拿掉**——双方点数相同时，服务端在一次请求内自动重掷双方直到分出先后（上限 100 次纯防御），先手必然一次掷骰流程内产生，广播消息会注明"双方同点 X，已自动重掷 N 次"。

### 改动与验证

- `server/src/index.ts`：`roll_dice` 中同点分支改为服务端 while 自动重掷双方，删除 `dice_tie` 事件发送；保留"旧版本遗留同点状态先清空"的兼容分支（救援热更新前卡在同点的房间）。
- `client/src/App.tsx`：删除永远不会触发的 `dice_tie` 监听；"重新掷骰"按钮保留用于兼容旧房间。
- 验证：服务端 `tsc` + 客户端 `tsc`/ESLint 通过；`restart-test.mjs` 全流程回归通过；**30 局掷骰风暴测试 30/30 全部分出先手**（期间自然出现 1 次首掷同点被自动重掷化解），无一次卡在掷骰阶段、先手判定与点数大小完全一致。

## 反馈 6：棋盘规格不应在创建房间时锁死，应每局开始前双方协商

### 你的想法

> 创建房间时不应该先确定棋盘的规格，而是创建房间后每次开始游戏前双方可以约定棋盘规格，可以一个人设置一个规格后询问对方是否同意，可以显示在聊天中，对方可以在那条消息上点是否同意，每次重新开始对局时也可以修改这个规格。

### 我的想法与设计

- 认同：规格本质上是"每一局的约定"，不该是房主的单向决定。设计成**提议-应答**机制，并把提议物化成一条**特殊的聊天消息**：
  - 创建房间时规格**可留空**（默认 4*4），创建不再是规格的决定点；
  - 等待准备阶段，任一方在侧栏输入 `m*n` 点"提议规格"→ 聊天里出现一张提议卡（提议人、规格、状态）；
  - 对方**直接在这条消息上点"同意/拒绝"**：同意 → 规格立即生效并清空双方准备状态（重新走准备→掷骰）；拒绝 → 提议作废；
  - 对方也可以**直接发新提议还价**（旧提议自动标记为已拒绝，始终只有一个待处理提议）；
  - 进入掷骰/对局阶段后提议通道关闭（未回应的提议自动作废），**每局重开回到等待阶段后可再次提议**——满足"每次重新开始对局时也可以修改"；
  - 对局进行中/掷骰中提议会被服务端拒绝，规格变更永远发生在局与局之间，不会篡改进行中的棋盘。

### 改动

- `server/src/index.ts`：`RoomState` 增加 `boardProposal`；聊天消息扩展 `kind: 'board-proposal'` 与 `proposal` 载荷（id/rows/cols/status）；新增 `propose_board`（校验 2-8、仅等待阶段、取代旧提议、写入聊天历史并广播）与 `respond_board`（不能回应自己的/失效提议；同意则改规格 + `resetRoundState`，拒绝则仅作废，聊天条目状态同步更新）；双方准备就绪时自动作废未回应提议（`invalidatePendingProposal`）；`resetRoundState` 清理提议状态。
- `client/src/App.tsx`：创建规格可留空；侧栏规格行在等待阶段变为"提议规格"入口（进行中锁定显示当前规格）；`proposeBoard()`/`respondBoard()`；`board_proposal_result` 监听；聊天消息按类型渲染提议卡（状态徽标：等待回应/✓已同意/✗已拒绝，非提议人可见同意/拒绝按钮）。
- `client/src/App.css`：提议卡、状态色、操作按钮样式（含深色模式）。

### 验证

- 服务端/客户端 `tsc` + ESLint 通过。
- 新增回归脚本 `client/proposal-test.mjs`（14 项断言全过）：默认 4*4 ✓ / 提议待处理 ✓ / 不能回应自己的 ✓ / 失效 id 拒绝 ✓ / 同意后规格生效+准备清空+聊天条目更新 ✓ / 拒绝后规格不变 ✓ / 非法规格拒绝 ✓ / 双方就绪自动作废未回应提议 ✓ / 掷骰阶段提议被拒 ✓。
- 浏览器实测：留空创建 → 对方发来"提议棋盘规格 5*3"卡片（同意/拒绝按钮）→ 点同意 → 顶部规格 chip 变 `5*3`、卡片变"✓ 已同意，规格已生效"、系统提示"请重新准备"。

## 反馈 11：复制链接大小写问题 + 开局前强制协商规格（含每局重确认）

### 你的想法

1. 复制的房间链接字母全大写，`?ROOM=` 解析不了（手动改回 `room` 才行）；另外房主开房后地址栏也应该直接变成 `localhost:5173/?room=房号`，统一起来；
2. 现在双方点准备就能直接开局进入默认 4*4，玩家可能没注意就跳过了规格协商。建议：把棋盘锁上并显式提醒；不应该默认 4*4 就能开局——4*4 可以先显示，但必须等一方提议、另一方同意后才能进入开局；锁定的 UI 和动画我自己考虑；
3. （追问）玩完一局开下一局时也应该有同样的协商 UI。

### 我的想法与实现

1. **链接**：解析改为大小写不敏感（遍历 searchParams 匹配 `room` 键，任何大小写变体都能识别）；开房/进房/旁观成功后用 `history.replaceState` 把地址栏同步为 `?room=房号`（不刷新页面），退回首页时清除——地址栏随时是可分享链接，与复制按钮产出的链接完全一致。
2. **首局强制协商**：完全采纳，且比"提醒"更进一步做了硬门槛——房间新增 `specAgreed` 标记，**只有提议被对方同意后才会置真**；未确认时 `player_ready` 被服务端直接拒绝（提示"开局前需先协商棋盘规格"），前端"准备开始"按钮同步禁用 + 橙色提示文案。棋盘区盖灰色锁定遮罩（🔒 棋盘规格待协商），文案随状态变化：无提议时引导去左侧提议 / 自己已提议时显示等待 / 对方提议时提示去聊天回应。4*4 仅作预览展示。
3. **每局重确认（追问的延伸）**：同意——但为避免每局两连点的摩擦，设计成"沿用或新提议"双通道：`resetRoundState` 每局重置 `specAgreed=false`（锁定），同时新增 `specAgreedOnce` 记录"是否曾确认过规格"；次局开始时锁定遮罩显示 **[沿用上一局 r*c]** 按钮（任一方一键确认，因为沿用现状无需对方再点头，新增 `confirm_spec` 事件），要改规格才走提议→同意流程；首局因无基础规格，只有提议通道。

### 踩坑记录

- 同意分支里先置 `specAgreed=true` 再调 `resetRoundState`（后者会重置该标记），导致确认立即被清、门禁永远打不开——已把置位挪到重置之后，回归测试全绿。

### 验证

- 双端 `tsc` + ESLint 通过；四套回归全过（restart 新增"未协商时准备被拒"与"一键沿用解锁次局"断言；multi-round 新增"默认 4*4 也须协商确认"断言）。
- 浏览器实测全流程：创建后 URL 带 `?room=`、锁定遮罩出现、准备禁用+橙色提示 → 提议 2*2 → 对方同意 → 遮罩解锁、准备可用 → 打完平局 → 投"我同意下一局" → 次局锁定遮罩带 **[沿用上一局 2*2]** → 点击后解锁，提示"已沿用 2*2 规格，可以准备开局了"。

## 反馈 13：同昵称问题修复 + 删除回合倒计时

### 你的想法

1. 两个人都设为一个昵称后会出现问题，怎么解决？
2. 不想要每轮的时间限制了，删去。

### 我的想法与实现

1. **同昵称问题拆成两层修**：
   - **房间内重名**：新玩家加入时若昵称（trim + 忽略大小写）与房间内玩家重复，服务端直接拒绝并提示"该昵称已被房间内玩家使用，请换一个昵称"——消除聊天与比分卡的指代混淆；
   - **同令牌双会话抢绑**：之前两个标签页用同一身份令牌时，presence_ping 会来回改写 `player.id`，导致落子随机失败。引入**页面随机标识（nonce）**：客户端每次页面加载生成随机 nonce，随 join/rejoin/presence_ping 上报；服务端仅当"nonce 相同（同页面断线重连）或该玩家本就离线"时才允许重新绑定，另一个标签页的 ping 无法抢回绑定——后加入的会话接管，先前的会话自动失效（落子被拒"你不在当前房间中"）。
   - 说明：昵称相同但浏览器不同仍是两个独立身份（令牌不同），服务端会拒绝重名让后者换名，这正是防冒充的预期行为。
2. **删除回合倒计时**：服务端移除 `TURN_TIMEOUT_MS`/定时器 Map/`syncTurnTimer`/`turnDeadline` 字段与房间销毁时的清理；客户端移除走秒状态、⏱ 显示、`turn_skipped` 监听与 `.turn-timer` 样式。行动权只在正常落子后交换。

### 验证

- 双端 `tsc` + ESLint 通过，倒计时相关引用清零；页面渲染正常无残留。
- 新增专项测试（6 项全过）：重名拒绝 ✓ / 不同昵称可加入 ✓ / 同令牌后到者接管 ✓ / 旧会话 ping 无法抢回绑定 ✓ / 旧会话落子被拒 ✓ / 新会话落子成功 ✓。
- 四套回归（restart / proposal / multi-round / resume）全部通过。
