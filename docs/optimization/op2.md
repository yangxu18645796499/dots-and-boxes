## 反馈 1：布局调整 + 重开一局 + 征求建议

### 你的想法（原话归纳）

1. **最大问题是页面布局**，含三个子问题：
   - 房间聊天应该放在**最右侧**，不该放下方；中间棋盘那部分太宽，正好用聊天栏平衡；
   - **棋盘位置不突出**、**当前回合该轮到谁不突出**，要我斟酌后调整；
   - 左侧栏布局仍可调整。
2. 页面应有**重开一局**选项：**当且仅当两个选手都同意**时才重开；重开相当于重新来一局，**之前的记录不变**。
3. 希望给出页面/功能上的改进、增删建议。

### 我的想法与设计决策

**布局（三栏结构）**
- 原 `280px + 弹性` 两栏里，中间列独占约 1300px，棋盘（最大 8×8 约 690px）居左漂着，聊天沉在底部只有 160px 高——空间分配失衡。
- 改为 `290px | 弹性中列 | 320px` 三栏：左=控制台，中=对局信息+棋盘，右=聊天。棋盘在面板内水平垂直居中，中列不再被拉满，视觉重心回到棋盘。
- 棋盘区从"固定 500px 高的空面板"改为 flex 居中容器，棋盘外围留白对称，配合发光描边强调。

**回合指示（三层强调）**
1. 顶部比分区改为「A 卡片 — 圆形回合勋章 — B 卡片」：轮到谁，谁的卡片**金色描边上浮**并挂"行动中"徽章，勋章显示 A/B 大字和当前回合方颜色；
2. 比分下方一条**整宽回合横幅**（轮到 A=蓝色渐变、轮到 B=橙色渐变、结束=灰色），自己回合时显示"🎯 轮到你了！"并带呼吸光圈动画；
3. 轮到你时**棋盘面板外框同色发光**（glow-a/glow-b），视线不用离开棋盘也知道该谁走。
- 原来散落在 status-grid 里的 7 行小字（房间/规格/状态/先手/结果…）压缩成顶部的圆角信息 chips + 一行小字，给棋盘让出垂直空间。

**左侧栏分组**
- 三段式：`房间`（昵称/规格/房号 + 创建/加入）、`操作`（准备、掷骰、重开投票、退回首页，全部通栏按钮）、`对战统计`（压缩成单行摘要 + 可滚动列表，最高 34vh），sticky 跟随滚动。
- 历史条目从 5 行压缩为 2 行（标题行 + 先手/比分/结果行）。

**重开一局（服务端权威的投票制）**
- 原逻辑：对局结束后**任意一方**点"再来一局"就直接开下一局，另一方没有否决权——正和你说的"当且仅当双方同意"冲突，所以整个换成投票制。
- 覆盖两个场景（同一个投票通道 `vote_next_round`）：
  - **对局进行中**：任一方发起，双方都同意 → 清盘重开**本局**（roundNumber 不变，`roundHistory`/`seriesScore` 完全不动，即"之前的记录不会变"），回到准备→掷骰流程；
  - **对局已结束**：原来的"再来一局"按钮升级为"同意再来一局"，双方都同意 → `roundNumber+1` 开下一局，历史与大比分保留。
- 投票可随时**再次点击撤回**（toggle），避免误触；任一方掉线其票自动作废。
- 结算从"浮在右侧的小面板（还要 JS 量宽度决定显隐）"改为**全屏毛玻璃遮罩 + 居中结算卡**，结果、比分、同意按钮、双方投票状态一目了然；顺带删掉了 ResizeObserver 那套估算逻辑。

## 反馈 5：掷骰逻辑有问题——双方同点后重掷一直同点

### 你的想法

> 投骰子部分我觉得逻辑有些问题，我刚才二者都摇到了 6，然后再往后二者的数就一直一样，随机摇数的逻辑要加强一下。

### 我的想法与排查

- 先说随机源：`crypto.randomInt(1, 7)` 是 Node 加密级随机、每次调用独立，**随机本身没有缺陷**，也不存在"两边摇到同一个数"的相关性 bug；
- 真正的问题在**同点重掷的交互设计**：旧逻辑双方同点后保持 {6,6} 展示、要求两人再各点一次"重新掷骰"，再同点就再来一轮——连续同点时体验就是"数一直一样"地循环点按钮（连续 n 次同点概率 (1/6)ⁿ，虽小但撞上一次就很难受）；
- **加强方案：同点死循环从交互里彻底拿掉**——双方点数相同时，服务端在一次请求内自动重掷双方直到分出先后（上限 100 次纯防御），先手必然一次掷骰流程内产生，广播消息会注明"双方同点 X，已自动重掷 N 次"。

### 改动与验证

- `server/src/index.ts`：`roll_dice` 中同点分支改为服务端 while 自动重掷双方，删除 `dice_tie` 事件发送；保留"旧版本遗留同点状态先清空"的兼容分支（救援热更新前卡在同点的房间）。
- `client/src/App.tsx`：删除永远不会触发的 `dice_tie` 监听；"重新掷骰"按钮保留用于兼容旧房间。
- 验证：服务端 `tsc` + 客户端 `tsc`/ESLint 通过；`restart-test.mjs` 全流程回归通过；**30 局掷骰风暴测试 30/30 全部分出先手**（期间自然出现 1 次首掷同点被自动重掷化解），无一次卡在掷骰阶段、先手判定与点数大小完全一致。

## 反馈 6：棋盘规格不应在创建房间时锁死，应每局开始前双方协商

### 你的想法

> 创建房间时不应该先确定棋盘的规格，而是创建房间后每次开始游戏前双方可以约定棋盘规格，可以一个人设置一个规格后询问对方是否同意，可以显示在聊天中，对方可以在那条消息上点是否同意，每次重新开始对局时也可以修改这个规格。

### 我的想法与设计

- 认同：规格本质上是"每一局的约定"，不该是房主的单向决定。设计成**提议-应答**机制，并把提议物化成一条**特殊的聊天消息**：
  - 创建房间时规格**可留空**（默认 4*4），创建不再是规格的决定点；
  - 等待准备阶段，任一方在侧栏输入 `m*n` 点"提议规格"→ 聊天里出现一张提议卡（提议人、规格、状态）；
  - 对方**直接在这条消息上点"同意/拒绝"**：同意 → 规格立即生效并清空双方准备状态（重新走准备→掷骰）；拒绝 → 提议作废；
  - 对方也可以**直接发新提议还价**（旧提议自动标记为已拒绝，始终只有一个待处理提议）；
  - 进入掷骰/对局阶段后提议通道关闭（未回应的提议自动作废），**每局重开回到等待阶段后可再次提议**——满足"每次重新开始对局时也可以修改"；
  - 对局进行中/掷骰中提议会被服务端拒绝，规格变更永远发生在局与局之间，不会篡改进行中的棋盘。

### 改动

- `server/src/index.ts`：`RoomState` 增加 `boardProposal`；聊天消息扩展 `kind: 'board-proposal'` 与 `proposal` 载荷（id/rows/cols/status）；新增 `propose_board`（校验 2-8、仅等待阶段、取代旧提议、写入聊天历史并广播）与 `respond_board`（不能回应自己的/失效提议；同意则改规格 + `resetRoundState`，拒绝则仅作废，聊天条目状态同步更新）；双方准备就绪时自动作废未回应提议（`invalidatePendingProposal`）；`resetRoundState` 清理提议状态。
- `client/src/App.tsx`：创建规格可留空；侧栏规格行在等待阶段变为"提议规格"入口（进行中锁定显示当前规格）；`proposeBoard()`/`respondBoard()`；`board_proposal_result` 监听；聊天消息按类型渲染提议卡（状态徽标：等待回应/✓已同意/✗已拒绝，非提议人可见同意/拒绝按钮）。
- `client/src/App.css`：提议卡、状态色、操作按钮样式（含深色模式）。

### 验证

- 服务端/客户端 `tsc` + ESLint 通过。
- 新增回归脚本 `client/proposal-test.mjs`（14 项断言全过）：默认 4*4 ✓ / 提议待处理 ✓ / 不能回应自己的 ✓ / 失效 id 拒绝 ✓ / 同意后规格生效+准备清空+聊天条目更新 ✓ / 拒绝后规格不变 ✓ / 非法规格拒绝 ✓ / 双方就绪自动作废未回应提议 ✓ / 掷骰阶段提议被拒 ✓。
- 浏览器实测：留空创建 → 对方发来"提议棋盘规格 5*3"卡片（同意/拒绝按钮）→ 点同意 → 顶部规格 chip 变 `5*3`、卡片变"✓ 已同意，规格已生效"、系统提示"请重新准备"。

## 反馈 7：聊天框发不出消息；要求 Enter 发送、Shift/Ctrl+Enter 换行

### 你的想法

> 房间聊天的聊天框发不出消息啊，应该支持点击发送或 Enter 键可以发送，并且 Shift+Enter 或 Ctrl+Enter 能换行输入。

### 我的想法与排查

- 找到"发不出"的根因：旧实现是单行 `<input>` 且 `onKeyDown` 里**任何 Enter 都会触发发送**——用中文输入法打字时，**按回车确认候选词的动作也被当成"发送"**（输入法组词期间 keydown 照样触发），导致要么发出空消息要么状态错乱，表现就是"发不出去"；
- 顺带把输入升级为多行 `<textarea>`，并明确三套按键行为：
  - **Enter**（无修饰键）→ 发送；
  - **Shift+Enter / Ctrl+Enter** → 在光标处插入换行。这里没有依赖浏览器默认行为，因为 Ctrl+Enter 在部分浏览器本来就不换行，各浏览器表现不一，改为显式插入保证一致（并恢复光标位置）；
  - **输入法组词中的回车**（`isComposing`）→ 只确认候选词，既不发送也不换行（本次 bug 的修复点）。
- 消息气泡加 `white-space: pre-wrap`，多行消息正常折行显示。

### 改动与验证

- `client/src/App.tsx`：聊天输入改 `textarea`（`rows=2`）+ `chatInputRef`；新增 `insertNewlineAtCaret()`（光标处插 `\n` 并恢复光标）；`onKeyDown` 按"组词→换行→发送"三段处理。
- `client/src/App.css`：textarea 样式（继承字体、禁用拖拽缩放）、`.chat-text` 支持换行显示。
- 追加打磨（同一反馈）：占位提示改为两行左对齐（"Enter 发送" / "Shift+Enter 换行"），发送按钮拉伸至与两行输入框同高（`align-items: stretch` + 按钮撑满列高），视觉上下对齐。
- `tsc` + ESLint 通过；浏览器实测：Shift+Enter 输入两行不发送 ✓ → Enter 发送 ✓ → 气泡按两行显示 ✓ → 输入框清空 ✓。

## 反馈 8：删除深色模式，只保留浅色

### 你的想法

> 删除深色模式吧，也就是右上角那几个也都不需要了，就保留浅色的。

### 我的想法

- 深浅双主题对这款游戏收益有限，却常年多维护一套 `data-theme` 变量、每个新组件都要写深色分支（本次改造里已经欠了好几处），删掉是对的——少一条状态轴，样式回归单一来源；
- 连同 `prefers-color-scheme` 监听、`localStorage` 主题持久化一并移除；CSS 变量只保留浅色值，老用户 localStorage 里的残留主题键不再被读取，页面恒为浅色。

### 改动与验证

- `client/src/App.tsx`：删除 `ThemeMode` 类型、`THEME_KEY`、`themeMode`/`effectiveTheme` 状态、`matchMedia` 监听 effect、`updateThemeMode()`、右上角主题切换按钮组。
- `client/src/App.css`：删除 `:root[data-theme='dark']` 变量块及所有深色覆盖规则（棋盘发光、聊天列表、提议卡）与 `.theme-switch/.theme-btn` 样式、响应式中的相关规则。
- `tsc` + ESLint 通过，主题相关引用清零；浏览器截图验证：右上角无切换按钮，页面恒为浅色，其余功能不受影响。

## 反馈 19：三栏动态等高（大棋盘整体撑高）+ 对战统计吸底

### 你的想法

### 验证
